\section{Program Structure}
\subsection{Purpose and scope}
This laboratory combines two small tasks: a logging library and a checker for round parentheses. The checker returns whether a string is valid, while the logger explains the steps taken to reach that answer. The program uses Java and its standard library; it does not require a separate logging framework.

The implementation supports the required levels, configurable message formatting, shared logger settings, and the optional random-phrase placeholder. Its four demonstration inputs are the ones listed in the handout. The project is opened in IntelliJ IDEA and started from \code{Main.main()}.

\subsection{Responsibilities of the four types}
\begin{tabularx}{\textwidth}{@{}p{56mm}Y@{}}
\toprule
\textbf{Source file} & \textbf{Responsibility}\\
\midrule
\code{Main.java} & Configures logging, creates a validator, and passes each example string to it.\\
\code{LogLevel.java} & Defines the four levels, their severity values, and their possible random phrases.\\
\code{Logger.java} & Stores the logger's name, filters messages, substitutes placeholders, and prints accepted entries.\\
\code{ParenthesesValidator.java} & Checks the order and matching of parentheses and reports events through a logger.\\
\bottomrule
\end{tabularx}

\subsection{How the parts collaborate}
\code{Main} creates one \code{ParenthesesValidator}. That validator contains a reference to a \code{Logger} named \code{Parentheses}. The logger consults \code{LogLevel} when deciding whether a message should appear and when choosing a random phrase.

\begin{center}
\fbox{\small Main $\rightarrow$ ParenthesesValidator $\rightarrow$ Logger $\rightarrow$ LogLevel}
\end{center}

This is a \emph{uses} relationship. The validator does not extend \code{Logger}: checking parentheses and printing diagnostic messages are different responsibilities. The logger can therefore also be used by another program.

The project repository is \href{https://github.com/itsjohnyoff/OOP-course}{itsjohnyoff/OOP-course}. This report explains the classes, their collaboration, and the checks performed on the current project. The following sections connect each laboratory requirement to the corresponding implementation behavior.

\section{Classes and Objects}
\subsection{Types, instances, and references}
A class defines the fields and methods available to its objects. The validator class provides \code{isValid()}. The \code{Logger} class provides methods such as \code{info()} and \code{error()}. The following statement in \code{Main} creates an actual validator object:
\begin{lstlisting}
ParenthesesValidator validator = new ParenthesesValidator();
\end{lstlisting}
The first \code{ParenthesesValidator} is the variable's type. The name \code{validator} identifies a local variable. The expression using \code{new} creates an object and invokes its constructor. The variable stores a reference to that object, which is used for calls such as \code{validator.isValid("()")}. No explicit constructor is declared in the validator, so Java supplies a default no-argument constructor.

\subsection{What state each object stores}
The validator has one instance field:
\begin{lstlisting}
private final Logger logger = new Logger("Parentheses");
\end{lstlisting}
Here, \code{Logger} is a type and \code{logger} is a field name. The string \code{"Parentheses"} is the name stored by the created logger, not the Java variable name. Another validator object would initialize its own logger object.

A logger stores an instance field called \code{name}. In contrast, \code{level} and \code{format} are shared class fields. The validator's input, character index, current character, and balance are method parameters or local variables. They are not stored as persistent validator fields. Every call therefore starts a fresh validation count.

\subsection{Encapsulation and the final reference}
\code{private} prevents code outside the validator from directly accessing its \code{logger} field. Other classes ask the validator to perform its job through the public \code{isValid()} method. They do not need access to its diagnostic collaborator.

\code{final} prevents reassignment of that field after initialization. It does not prevent calls to \code{logger.info(...)} and does not make all logger configuration immutable. Likewise, the logger's \code{private final String name} is assigned during construction and cannot later be replaced through that field.

\code{Main.main()} is static, so the entry point is invoked without creating a \code{Main} object. \code{LogLevel} is an enum: its constants are predefined instances carrying severity and phrase data.

\section{Static and Instance Members}
\subsection{One name per object; one shared configuration}
The distinction is visible directly in \code{Logger.java}:
\begin{lstlisting}
private final String name;
private static LogLevel level = LogLevel.INFO;
private static String format = "[%t] [%l] %n: %m";
\end{lstlisting}
The \code{name} field belongs to each logger object. Two objects can therefore identify different parts of a program. The \code{static} fields belong to the class and are consulted by every logger instance. Storing the minimum level and format this way gives all loggers one common configuration.

The setters are also static, so they are called through the class:
\begin{lstlisting}
Logger.setLevel(LogLevel.TRACE);
Logger.setFormat("[%t] [%l] %n: %m | %r");
\end{lstlisting}
These are the settings chosen by \code{Main}. They override the initial defaults before the four examples are checked. The setter methods reject null values using \code{Objects.requireNonNull()}.

\subsection{How the minimum level works}
The enum assigns severity values 10, 20, 30, and 40 to TRACE, INFO, WARN, and ERROR. Its comparison is:
\begin{lstlisting}
public boolean allows(LogLevel messageLevel) {
    return messageLevel.severity >= this.severity;
}
\end{lstlisting}
When called as \code{level.allows(messageLevel)}, \code{this} is the configured minimum level. A message is accepted when its severity is at least that minimum.

\begin{tabularx}{\textwidth}{@{}lY@{}}
\toprule
\textbf{Configured level} & \textbf{Messages printed}\\
\midrule
TRACE & TRACE, INFO, WARN, ERROR\\
INFO & INFO, WARN, ERROR\\
WARN & WARN, ERROR\\
ERROR & ERROR only\\
\bottomrule
\end{tabularx}

The static \code{TIME\_FORMAT} field is different from the mutable configuration: it is a shared final reference to the reusable \code{DateTimeFormatter} for \code{HH:mm:ss} timestamps. The enum's \code{severity} and \code{phrases} are instance fields belonging to each enum constant.

\subsection{Demonstrating shared settings}
The following small experiment uses two separate logger objects. It is a verification example rather than an additional feature of \code{Main}.
\begin{lstlisting}
Logger first = new Logger("First");
Logger second = new Logger("Second");

Logger.setLevel(LogLevel.ERROR);
Logger.setFormat("%n/%l/%m");
first.info("hidden");
first.error("one");
second.error("two");
\end{lstlisting}
Expected output:
\begin{lstlisting}[language={}]
First/ERROR/one
Second/ERROR/two
\end{lstlisting}
Both objects use the new level and format, even though they were created before the setters were called. Their names remain different because the name belongs to each object. The INFO entry is filtered out before formatting and printing.

Changing the shared configuration again affects existing objects:
\begin{lstlisting}
Logger.setLevel(LogLevel.TRACE);
Logger.setFormat("[%l] %n: %m");
first.trace("visible now");
second.info("same configuration");
\end{lstlisting}
This time, both messages are accepted. Creating a third logger would not create a third independent level or format: it would consult the same static fields.

\subsection{Why these choices fit the laboratory}
Instance names identify the source of an entry, while static configuration avoids setting the same options separately on every object. Keeping the fields private means configuration changes go through the public setters, where invalid null values can be rejected.

The shared settings also have a consequence: changing the format for one demonstration changes it for every subsequent logger call. Tests must restore the configuration they depend on. The current application uses one thread and changes settings before validation; it does not claim to provide synchronized configuration for concurrent callers.

The validator's final logger reference and the logger's static settings solve different problems. The final reference prevents replacement of a collaborator. Static fields establish shared state; they do not prevent that state's values from changing.

\section{Methods and Responsibilities}
\subsection{The logger's message pipeline}
The public methods \code{trace()}, \code{info()}, \code{warn()}, and \code{error()} are convenient entry points. Each supplies its level to \code{log()}. For example:
\begin{lstlisting}
public void info(String message) {
    log(LogLevel.INFO, message);
}
\end{lstlisting}
The responsibility of \code{log()} is to reject null arguments, apply the minimum-level filter, and print an accepted message. Formatting is delegated to the private \code{formatMessage()} helper.
\begin{lstlisting}
if (!level.allows(messageLevel)) {
    return;
}
System.out.println(formatMessage(messageLevel, message));
\end{lstlisting}
This early \code{return} leaves the void logging method without printing. It does not stop validation, because the validation method continues after its logger call.

\subsection{Formatting an accepted entry}
The formatter scans a local copy of the template and appends output to a \code{StringBuilder}. Ordinary characters are copied. A recognized percent placeholder is replaced, and its letter is skipped so that it is not printed twice.

\begin{tabularx}{\textwidth}{@{}lY@{}}
\toprule
\textbf{Placeholder} & \textbf{Replacement}\\
\midrule
\code{\%t} & Current local time formatted as \code{HH:mm:ss}.\\
\code{\%l} & Level of this entry, such as INFO.\\
\code{\%n} & This logger object's name.\\
\code{\%m} & Original message text.\\
\code{\%r} & Random phrase associated with this entry's level.\\
\bottomrule
\end{tabularx}

An unknown placeholder such as \code{\%x} is preserved. A final percent character is preserved too. Values inserted from a name or message are not scanned again, so a message containing \code{\%l} keeps that literal text.

For \code{\%r}, \code{messageLevel.randomPhrase()} selects from that enum constant's phrases using \code{ThreadLocalRandom}. The formatter caches the choice within one entry, so repeated \code{\%r} placeholders agree. A later entry may choose another phrase. The choice affects presentation, never the validation answer.

\subsection{The validator's character loop}
\code{isValid(String input)} receives one complete string and returns a primitive \code{boolean}. Null is rejected before accessing the string's length. The method then initializes a local balance to zero and reads one character at a time:
\begin{lstlisting}
int balance = 0;
for (int i = 0; i < input.length(); i++) {
    char current = input.charAt(i);
    // One branch handles the current character.
}
\end{lstlisting}
The branches are mutually exclusive. An opening increases balance and produces TRACE. A closing first checks whether an unmatched opening is available. If balance is zero, the validator warns and returns an invalid result immediately. Otherwise it decreases balance and logs a completed pair at INFO. Any other character is rejected.

For \code{(())}, the state changes as follows:

\begin{tabularx}{\textwidth}{@{}cccY@{}}
\toprule
\textbf{Index} & \textbf{Character} & \textbf{Balance} & \textbf{Event}\\
\midrule
0 & \code{(} & 1 & TRACE: opening found\\
1 & \code{(} & 2 & TRACE: opening found\\
2 & \code{)} & 1 & INFO: matching pair\\
3 & \code{)} & 0 & INFO: matching pair\\
\bottomrule
\end{tabularx}

After the loop, a positive balance means some openings remain unmatched. A zero balance means the input is valid, provided no earlier rejection occurred. Indexes in messages are zero-based.

\subsection{Reporting failure without duplicating code}
\begin{lstlisting}
private boolean reportInvalid(String input, String reason) {
    logger.error("Invalid input \"" + input + "\": " + reason);
    logger.info("Validation result for \"" + input + "\": false");
    return false;
}
\end{lstlisting}
\code{return reportInvalid(input, reason)} first executes this helper, then returns its false result from \code{isValid()}. It ends only that call, so \code{Main}'s loop can check the next string. This is a method call between collaborating objects when the helper invokes \code{logger.error(...)}. The separate logger keeps filtering and formatting out of the validation algorithm.

\subsection{The four required examples}
The demonstration in \code{Main} uses the exact input strings required by the handout. TRACE is enabled and the format is \code{[\%t] [\%l] \%n: \%m | \%r}. Therefore timestamps, opening events, completed pairs, failures, and final results are visible.

\textbf{Input} & \textbf{Expected} & \textbf{Observed} & \textbf{Reason}\\
\midrule
\code{()} & true & true & One opening followed by its closing.\\
\code{)((()))} & false & false & An unmatched closing appears at index 0.\\
\code{(} & false & false & One unmatched opening remains at the end.\\
\code{(())((()())())} & true & true & All pairs match in the correct order.\\

The required inputs passed. The final Boolean returned by \code{isValid()} agrees with the final INFO message. \code{Main} currently ignores that returned value, because the validator already reports its result through the logger.

\subsection{Reading one successful run}
For \code{()}, the core messages are:
\begin{lstlisting}[language={}]
[TRACE] Parentheses: Opening parenthesis found at index 0; unmatched openings: 1
[INFO] Parentheses: Matching pair completed at index 1
[INFO] Parentheses: Validation result for "()": true
\end{lstlisting}
Timestamps and the random suffix have been omitted here for readability. The first line follows \code{balance++}; the second follows \code{balance--}; the third follows the successful end-of-input check. The current format includes \code{\%t}, so the actual console output displays the local time before each level.

For \code{)((()))}, checking stops at the first character. It is unnecessary to inspect the remaining characters: a later opening cannot repair a closing that has already appeared too early. The WARN line describes the unmatched closing, and \code{reportInvalid()} supplies the ERROR explanation and false final result.

An ERROR line in this output is a deliberate diagnostic entry, not an uncaught Java exception. Invalid example inputs are expected test cases, and the loop proceeds to the next example.

\subsection{Additional validation cases}
The required examples cover basic success and failure, but extra cases check boundaries and repeated use of one validator object.

\begin{tabularx}{\textwidth}{@{}p{35mm}cY@{}}
\toprule
\textbf{Input} & \textbf{Result} & \textbf{Behavior checked}\\
\midrule

\code{()()} & true & Consecutive independent pairs.\\
\code{((()))} & true & Several nested pairs.\\
\code{)(} & false & Correct total counts do not imply correct order.\\
\code{())} & false & Extra closing after a completed pair.\\

The \code{)(} case is especially useful for preventing an incorrect solution that compares only the total number of openings and closings. Its totals are equal, but its first closing has no available opening. The early \code{balance == 0} check is necessary.

\subsection{A fresh count for each call}
The same object was checked with an invalid input followed by a valid one. The valid input still returned true. This checks that the previous call's state does not leak into the next call. The declaration \code{int balance = 0} inside \code{isValid()} ensures a new count for every invocation.

The verification also included 2,000 nested pairs and a string of 2,000 unmatched openings. These cases exercise a longer scan without recursion or a stack in the submitted validator. They do not establish a general performance benchmark; they check the behavior of the same counter logic on longer inputs.

Null input is handled as a validation failure, while null arguments supplied directly to the logger are rejected by its argument checks. These are separate contracts: \code{isValid(null)} returns false, but constructing \code{new Logger(null)} is not accepted.

A temporary standard-library test harness was compiled against the current four source files. It is kept outside the submitted \code{src} tree. The verification completed with:

The checks include assertions within repeated and generated cases; the number does not mean 2,512 separate hand-written test methods. Every parentheses string of length 0 through 10 was compared with an independent stack-based reference checker. That contributes 2,047 generated inputs.

Filtering was checked at all four configured levels by sending one entry of each level and comparing the visible output with the table in Section 3. Validation results were also checked at every level. Raising the minimum hides some entries, but it does not change true to false or false to true.

\subsection{Formatting and bonus checks}
The formatting checks covered \code{\%t}, \code{\%l}, \code{\%n}, and \code{\%m}, as well as repeated placeholders, an empty template, unknown placeholders, and a trailing percent sign. The time value was checked for the \code{HH:mm:ss} shape and against the current time around the logging call.

The literal-substitution case used placeholder-like text inside a logger name and message. That text remained unchanged after insertion. This checks that the formatter processes only its template, rather than repeatedly replacing tokens inside the output it has already built.

For the bonus, multiple messages were logged at each level. Each generated phrase was checked against the phrases for that entry's level. Two \code{\%r} placeholders in one template were also checked for equality within that entry. The checks do not require different runs to choose different phrases: random selection may legitimately repeat a value.

Shared-state checks used separate logger objects with different names. Updating the static settings affected both existing objects and an object created later, while all three retained their individual names. The harness restored the standard level and format after completion so that test configuration would not be mistaken for the application defaults.

\subsection{Why the counter algorithm is correct}
Before each character is processed, balance represents the number of openings in the already-read prefix that have not yet been matched. Initially the prefix is empty and balance is zero.

An opening adds one unmatched opening, so incrementing balance preserves that meaning. A closing consumes one available opening, so decrementing a positive balance preserves it too. If balance is zero when a closing appears, the prefix is already invalid; no later character can change the order of that prefix. Rejecting immediately is therefore correct.

If the entire string is processed without rejection, a positive final balance means openings remain. A zero final balance means every opening has a closing and every closing had an earlier opening. Both matching and ordering requirements are satisfied. Characters outside the permitted alphabet are rejected explicitly.

\subsection{Cost and practical limits}
For an input of length \code{n}, the validation scan visits each character at most once. Its decision logic takes \(O(n)\) time in the worst case and uses \(O(1)\) auxiliary space: a balance counter, an index, and the current character. An early failure can inspect fewer than \code{n} characters.

These bounds describe the validation algorithm. Logging also constructs strings, scans a format template, and writes output. In particular, a final message contains the input itself, so diagnostic text can require space proportional to the input length. The overall program should not be described as allocating only constant space.

\subsection{What the results demonstrate}
The required examples and additional checks support the implemented behavior for round parentheses. They also check that presentation choices do not alter the Boolean decision. They are not evidence that the logger is a production logging framework.

The implementation intentionally uses the console, the system clock, and shared mutable configuration. It has no log-file output, asynchronous processing, or defined concurrent-update behavior. The input policy is strict: spaces, letters, square brackets, and curly brackets are invalid. Extending those policies would require an explicit design change rather than a different logging format.

\section{Reflection}
\subsection{The most important OOP concept}
The main design lesson is the separation of responsibilities through collaborating objects. The validator owns the correctness decision. Its logger owns the presentation of diagnostic events. Calling \code{logger.info(...)} lets the validator describe an event without implementing severity comparisons, timestamps, or template parsing itself.

Encapsulation makes this relationship clear. Outside code calls \code{isValid()} instead of reaching into the private logger field. The final reference expresses that the validator keeps the same collaborator after construction. At the same time, the static configuration demonstrates shared state: logger objects have separate names but consult one common level and format.

This implementation also makes the distinction between object state and method-local state concrete. The logger reference survives between calls. The balance counter does not; it starts at zero each time. Moving balance into an instance field without resetting it would create a risk of incorrect results across calls.

\subsection{Improvements to consider}
One useful improvement would be an optional constructor that accepts a logger. A default constructor could still create the named console logger for the laboratory. Supplying the collaborator would make it easier to capture output or replace diagnostics during testing without changing the parentheses algorithm.

Another improvement would be to make the output destination and time source configurable. Direct calls to \code{System.out.println()} and \code{LocalTime.now()} are sufficient for this demonstration, but an injected output stream and clock would make logger checks more deterministic. The required shared level and format could remain static.

For a multi-threaded application, configuration updates would need a defined synchronization strategy. Simply copying the format reference into a local variable does not make all shared settings thread-safe. That additional machinery is outside the scope of the current single-threaded program.

\subsection{Explaining the implementation}
The central questions are answerable directly from the source: why a name belongs to an object, why level and format are static, why \code{)(} fails despite equal character counts, and why a filtered INFO message does not change the returned Boolean. Understanding those points is more useful than memorizing console output, especially because the random suffix can change between runs.
